# LeanFlow Orchestrate

Use this strategy only for a user request for the specification → planning → implementation workflow, with any stated stage restrictions; a generic build or implementation request is not enough. It composes [`../leanflow-to-spec/SKILL.md`](../leanflow-to-spec/SKILL.md), [`../leanflow-plan/SKILL.md`](../leanflow-plan/SKILL.md), and [`../leanflow-execute/SKILL.md`](../leanflow-execute/SKILL.md). Read their actual bodies before the respective stages; they own specification synthesis, method selection, plan format, artifact privacy, implementation, and verification. The current agent coordinates scope, the required specification file, shared-plan state, integration, and acceptance.

1. Resolve objective, scope, constraints, and acceptance criteria. Orchestration authorizes specification, planning, then implementation only within the requested task and actual permissions; planning-only consent allows specification then planning, not implementation, and a specification-only request stops after specification. Read-only limits still apply. If material choices remain, use [`../leanflow-brainstorm/SKILL.md`](../leanflow-brainstorm/SKILL.md) before committing to an approach; do not repeat settled decisions or proceed past unresolved material design.
2. Discover the host's available delegation interface and permitted roles before drafting. Use supported workers, not invented agent names, model tiers, runtime flags, or tool aliases. If delegation is unavailable, disclose and perform authorized stages directly only when direct work is permitted. An explicit delegation-only constraint makes unavailable or forbidden delegation a blocker; do not silently take over. The coordinator remains the sole specification/shared-plan writer even when workers research or draft.
3. Create a source-grounded specification using the actual `leanflow-to-spec` procedure and the artifact privacy procedure owned by `leanflow-plan`. When delegating a read-only draft, read and supply the [assignment packet](references/delegation.md#assignment-packet); the coordinator validates the returned draft against the source and alone creates the required new, non-colliding `.workflow/specification/<SEQ>-YYYYMMDD-<slug>-spec.md` under those canonical rules. Preserve existing records; do not migrate older directories. If required writes or privacy cannot be established, return the complete specification through a permitted channel with the blocker and stop dependent planning and implementation. An inline draft or launch receipt does not satisfy this required file. Surface unresolved material design and stop dependent work even if a draft can be saved.
4. Read that exact saved specification as planning input and complete canonical `leanflow-plan` planning. Let it choose flash, super, or hyper from evidence unless the user requested a method. Delegate read-only research/drafting when supported, then validate the returned method, plan, and rationale. If an exact plan was supplied, still create and read the specification first, then validate that supplied plan against it, current evidence, and consent during this planning stage; do not silently replace it. Material inconsistencies require a blocker or `REPLAN_REQUIRED` under the existing authorization/revision boundaries. The coordinator alone saves a resulting plan under canonical privacy rules, or retains its complete content in chat. Preserve a supplied plan's meaning and identity. A launch receipt is not completed planning.
5. Only after the specification file and planning stage are complete, execute that exact resulting or validated supplied plan, saved or inline, under canonical execution and within consent. Planning-only consent stops after reporting the plan. Split only independent work with bounded nonoverlapping write ownership and explicit shared contracts; sequence true dependencies and retain one integration owner. Before dispatching any worker, read and supply the [assignment packet](references/delegation.md#assignment-packet). Workers load the applicable core and delegation reference, return results and evidence, and never recursively orchestrate.
6. Keep a single writer for shared-plan state: the coordinator alone updates the shared plan, step status, and aggregate evidence throughout delegated work. Assign stable step IDs to inline steps if absent, without changing their meaning. Workers return their assigned IDs and evidence; no worker receives shared-plan write ownership. For parallel implementation, reserve combined gates for the coordinator after all relevant workers finish; assign any independent worker checks explicitly.
7. Wait for actual results before dependent work or acceptance. On failure, report it and resolve worker status and partial effects before recovery within authorization. Do not blindly retry, replay completed work, or conceal a switch to direct execution; delegation-only constraints still apply.
8. Integrate results and exercise the combined consumer path with authorized checks. Check actual changes and evidence against acceptance criteria, not worker status alone. When independent source review is requested or justified by concrete risk, read and apply [delegated review](references/delegation.md#delegated-review); it is not mandatory.
9. Report the exact specification and plan sources, observed outcomes, verification, blockers, and unavailable capabilities. For substantial English or Indonesian reports, read the shared [writing guidance](../leanflow-to-spec/references/writing.md). Do not finish at handoff receipts while required work remains running. Specification creation alone does not authorize later stages; the orchestration request supplies that authorization only within its stated scope and limits.
   Apply execution's [completion boundary](../leanflow-execute/SKILL.md#completion-boundary): report implementation verification separately from independent review and delivery readiness. Do not imply that finishing orchestration establishes current CI, human acceptance, or merge authorization.

`REPLAN_REQUIRED` permits at most one coordinator-led automatic revision within original authorization and only when replanning is permitted. Preserve the old plan, include decisive evidence and completed work, and do not replay verified steps. Broader scope requires the user's decision; a second material invalidation stops dependent work.

Native roles and prose specify intended tool policy, not OS containment or guaranteed suppression of ambient tools. Respect inherited tools and host permissions; do not change model or approval settings. No automatic commits, pushes, FSMs, or ledgers.
