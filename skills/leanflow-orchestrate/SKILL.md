# LeanFlow Orchestrate

This explicitly selected strategy composes [`../leanflow-to-spec/SKILL.md`](../leanflow-to-spec/SKILL.md), [`../leanflow-plan/SKILL.md`](../leanflow-plan/SKILL.md), and [`../leanflow-execute/SKILL.md`](../leanflow-execute/SKILL.md). Read their actual bodies before the respective stages; they own specification synthesis, method selection, plan format, artifact privacy, implementation, and verification. The current agent coordinates scope, the required specification file, shared-plan state, integration, and acceptance.

1. Resolve objective, scope, constraints, and acceptance criteria. Orchestration authorizes specification, planning, then implementation only within the requested task and actual permissions; planning-only consent allows specification then planning, not implementation, and a specification-only request stops after specification. Read-only limits still apply. If material choices remain, use [`../leanflow-brainstorm/SKILL.md`](../leanflow-brainstorm/SKILL.md) before committing to an approach; do not repeat settled decisions or proceed past unresolved material design.
2. Discover the host's available delegation interface and permitted roles before drafting. Use supported workers, not invented agent names, model tiers, runtime flags, or tool aliases. If delegation is unavailable, disclose and perform authorized stages directly only when direct work is permitted. An explicit delegation-only constraint makes unavailable or forbidden delegation a blocker; do not silently take over. The coordinator remains the sole specification/shared-plan writer even when workers research or draft.
3. Create a source-grounded specification using the actual `leanflow-to-spec` procedure and the artifact privacy procedure owned by `leanflow-plan`. A permitted read-only worker may return a draft under the **Assignment packet** below; the coordinator validates it against the source and alone creates the required new, non-colliding `.workflow/specification/<SEQ>-YYYYMMDD-<slug>-spec.md` under those canonical rules. Preserve existing records; do not migrate older directories. If required writes or privacy cannot be established, return the complete specification through a permitted channel with the blocker and stop dependent planning and implementation. An inline draft or launch receipt does not satisfy this required file. Surface unresolved material design and stop dependent work even if a draft can be saved.
4. Read that exact saved specification as planning input and complete canonical `leanflow-plan` planning. Let it choose flash, super, or hyper from evidence unless the user requested a method. Delegate read-only research/drafting when supported, then validate the returned method, plan, and rationale. If an exact plan was supplied, still create and read the specification first, then validate that supplied plan against it, current evidence, and consent during this planning stage; do not silently replace it. Material inconsistencies require a blocker or `REPLAN_REQUIRED` under the existing authorization/revision boundaries. The coordinator alone saves a resulting plan under canonical privacy rules, or retains its complete content in chat. Preserve a supplied plan's meaning and identity. A launch receipt is not completed planning.
5. Only after the specification file and planning stage are complete, execute that exact resulting or validated supplied plan, saved or inline, under canonical execution and within consent. Planning-only consent stops after reporting the plan. Split only independent work with bounded nonoverlapping write ownership and explicit shared contracts; sequence true dependencies and retain one integration owner. Prepare the **Assignment packet** below for every worker. Workers read the applicable canonical procedure, return results and evidence, and never recursively orchestrate.
6. Keep a single writer for shared-plan state: the coordinator alone updates the shared plan, step status, and aggregate evidence throughout delegated work. Assign stable step IDs to inline steps if absent, without changing their meaning. Workers return their assigned IDs and evidence; no worker receives shared-plan write ownership. For parallel implementation, reserve combined gates for the coordinator after all relevant workers finish; assign any independent worker checks explicitly.
7. Wait for actual results before dependent work or acceptance. On failure, report it and resolve worker status and partial effects before recovery within authorization. Do not blindly retry, replay completed work, or conceal a switch to direct execution; delegation-only constraints still apply.
8. Integrate results and exercise the combined consumer path with authorized checks. Check actual changes and evidence against acceptance criteria, not worker status alone. Use the **Delegated review** procedure when independent source review is requested or justified by concrete risk; it is not mandatory.
9. Report the exact specification and plan sources, observed outcomes, verification, blockers, and unavailable capabilities. Do not finish at handoff receipts while required work remains running. Specification creation alone does not authorize later stages; the orchestration request supplies that authorization only within its stated scope and limits.

## Assignment packet

Provide each worker a self-contained packet, not only a role name or a reference to conversation history:

- **Task, specification, and plan:** objective, stage, constraints, acceptance criteria, and the exact saved specification path with access instructions when present or required. For specification drafting, provide the complete source material or exact accessible source paths/conversation excerpts and state that the specification is not saved yet. Standalone planning/execution may explicitly state that no specification was requested. Provide the exact selected plan path with access instructions, or its complete inline content, when one exists; for research/specification/planning drafts with no plan, explicitly say **no plan exists yet** rather than inventing a path or step IDs. Identify assigned step IDs when available and pending work; include settled decisions and relevant completed-step evidence. Orchestrated planning and execution require access to the exact saved specification, not an inline substitute.
- **Source resolution:** workspace/source root, bases for relative specification, source-material, and plan references, and actual locations or supported discovery routes for the applicable canonical skill bodies. Specification drafters read `leanflow-to-spec`; planners read `leanflow-plan`; executors read `leanflow-execute`. Relative links resolve from the file containing them, not the worker's assumed working directory. Missing access to required content blocks that dependent work.
- **Ownership and dependencies:** exact writable paths/areas, read-only context, exclusions, shared interfaces, prerequisites, and integration owner. Identify the coordinator as sole specification/shared-plan writer; drafting workers return content without saving either artifact. Do not assign overlapping writes.
- **Permissions and checks:** read/write/execution limits, destructive/external-effect consent, explicit delegation-only constraints, allowed assigned checks with expected observations, coordinator-reserved gates, and actions requiring a blocker or `REPLAN_REQUIRED`. Role declarations do not widen authority.
- **Return evidence:** assigned stage and step IDs when available, source citations or changed paths, results, exact checks/observations, unrun checks and reasons, blockers, and partial effects. Require actual results, not a launch receipt. Workers must not invoke other workers or orchestration workflows.

## Delegated review

Give the reviewer the supplied changes or source boundary, plan/acceptance criteria, and relevant evidence through the assignment packet. It inspects source only: no edits, command execution, payload execution, or delegation. Return actionable findings ordered by severity with exact file/line citations, impact, and a concise correction; distinguish unsupported concerns from demonstrated defects. If none are found, state the inspected scope and limitations. Supplied check evidence is not a check the reviewer ran.

`REPLAN_REQUIRED` permits at most one coordinator-led automatic revision within original authorization and only when replanning is permitted. Preserve the old plan, include decisive evidence and completed work, and do not replay verified steps. Broader scope requires the user's decision; a second material invalidation stops dependent work.

Native roles and prose specify intended tool policy, not OS containment or guaranteed suppression of ambient tools. Respect inherited tools and host permissions; do not change model or approval settings. No automatic commits, pushes, FSMs, or ledgers.
