# LeanFlow PR Work

Translate the authorized issue/change into useful PR material and, when requested, a bounded implementation. This is not an automation engine or a grant of Git/GitHub authority. A request to draft a PR does not authorize implementation, branches, commits, pushes, or publication.

1. **Bound the request.** Establish the repository, issue/change, current branch, head/base evidence, permitted actions, acceptance criteria, exclusions, and material unknowns. Inspect available facts before asking. Do not copy another PR's refs onto this change. Label proposed or unknown refs explicitly.
2. **Use the appropriate implementation path only when requested.** For unresolved consequential choices, read [brainstorming](../leanflow-brainstorm/SKILL.md). For planning-only requests, read [planning](../leanflow-plan/SKILL.md) and stop after the plan. For authorized execution of an exact supplied plan, read [execution](../leanflow-execute/SKILL.md). When the user explicitly selects end-to-end orchestration, read [orchestration](../leanflow-orchestrate/SKILL.md); its required saved specification and planning stages still apply. Otherwise implement only the bounded requested change through the host's permitted tools; do not make orchestration or a saved plan mandatory for ordinary work. A PR-draft or review-only request remains nonmutating.
3. **Keep Git actions explicit.** Suggest a branch name if useful; do not create/switch branches or worktrees implicitly. Before drafting a needed commit message, read [commit-message guidance](../leanflow-commit-message/SKILL.md); that owner handles staged precedence, history style, and read-only advice. Do not commit, amend, push, force-push, publish, close, delete, merge, or release unless that action was requested. Native permissions still apply; resolve a newly introduced material consequence before dependent action.
4. **Verify within scope.** For implementation, run relevant authorized checks and exercise the changed consumer path where practical. For drafting-only work, inspect supplied/current evidence without inventing a new implementation or running unrelated checks. Distinguish observed results, supplied claims, and unrun checks. A review request calls for findings, not fixes. When independent source review is requested, read the [canonical delegated-review procedure](../leanflow-orchestrate/references/delegation.md#delegated-review) without starting orchestration or granting delegation authority.
   Before substantial implementation, apply execution's [verification-readiness procedure](../leanflow-execute/SKILL.md#verification-readiness), including for bounded work that does not require a plan. Drafting-only work does not run baseline checks or create validation scaffolding.
5. **Draft before publishing.** Inspect applicable repository guidance and PR templates. Follow the user's explicit format first, then the applicable repository structure; avoid duplicate sections. With neither, use these slots: **Refs** (source/request, head, base; mark suggested/not-created or unknown), **Summary and scope**, **Related issue** (none supplied if absent), **Verification** (observed and unrun), and **Limits**. Do not invent issue numbers, refs, screenshots, passing results, or closing keywords. Include closing keywords only when requested. Return title/body through the permitted response channel unless publication was explicitly requested.
   Include a delivery handoff within the chosen format, not a competing template. Identify the current head revision and any uncommitted changes, then report: **CI** (required checks, status, and checked revision; older-head results are stale and do not cover later local edits), **independent review** (reviewer/source, inspected revision/scope, findings and limits), **actionable feedback** (unresolved items or evidenced dispositions; a fix is not proof that a thread is resolved), and **human/manual checks** (required target-environment or visual checks, observed results, and remaining human decisions). Use explicit unknown, unavailable, pending, stale, or not-applicable states with reasons instead of treating missing evidence as success. Match repository/user requirements; do not require a new service, reviewer, or CI setup for every task.
   After authorized review fixes, rerun affected checks and refresh head-specific CI/review evidence when available; earlier evidence does not automatically cover the fix. Keep implementation, verification, and independent review distinct under execution's [completion boundary](../leanflow-execute/SKILL.md#completion-boundary). Report unmet delivery requirements and the next human decision without claiming ready-to-merge status while required evidence is missing. Do not resolve threads, request reviews, change CI/settings, push, or merge merely to complete this handoff; each external action still needs its corresponding authorization.
6. **Make material changes reviewable.** Lead with core behavior and primary files, then integration, mechanical/generated edits, and high-risk boundaries. Use a compact visual where it clarifies behavior or structure: pseudocode, a flow/component tree, a shallow file tree, or a focused diff. For material changes, include concrete before/after evidence when available (screenshots for visual changes; otherwise observed output/tests); mark missing or unrun evidence rather than fabricate it. Describe merge reversibility as a one-way or two-way door, explain why, and name the blast radius and affected consumers. Fit these details into the selected format instead of imposing another template on small diffs. Suggest splitting genuinely independent concerns when needed; do not rewrite history or disguise behavior changes as cleanup.
7. **Return the bounded result.** State actual implementation status if applicable, the draft title/body, checks and limits, and concrete remaining actions. If asked to publish/update a PR, use the host's available authorized interface for only the requested change and verify its returned state. If unavailable, report that boundary and return the complete draft; do not claim publication. Do not contact others or change unrelated issues, labels, reviewers, or repository settings implicitly.

The two Git skills are optional workflows, not extra orchestration stages. No native role, provider, model, service, or credential configuration is required by this procedure.
