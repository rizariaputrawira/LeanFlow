# Compare materially different interfaces

Read when the request calls for alternative interface designs for a concrete candidate. This is a design exercise, not a requirement to dispatch agents or build prototypes. Use permitted delegation only when independently useful and allowed by the assignment; a single thoughtful comparison is sufficient. Helpers inherit the same read-only/planning limits.

1. **Frame the constraints.** State requested behavior, affected callers, invariants, and dependencies; use [deepening](deepening.md) where dependency strategy matters. Distinguish sourced constraints from assumptions. An illustrative in-chat sketch can clarify a constraint but must not preselect the answer.
2. **Develop distinct shapes.** Explore interfaces that optimize meaningfully different concerns: minimum surface, common-caller simplicity, needed flexibility, or explicit ports/adapters where actual implementations justify them. Renaming the same methods is not a second design. Do not invent hypothetical consumers merely to justify an abstraction.
3. **Make each option concrete.** Show entry points/types and a caller example, plus invariants, ordering, errors, configuration, and performance obligations. Identify hidden behavior, dependencies/adapters, leverage, locality, test surface, migration impact, and trade-offs. Sketches remain proposals, not compiled or executed evidence.
4. **Compare on the same criteria.** Evaluate depth, caller burden, locality, seam placement, actual variation, compatibility, and operational consequences. Recommend the strongest fit, or a hybrid only when its parts compose without undermining clarity. Prefer a simpler adequate design over speculative flexibility.
5. **Close the decision honestly.** State the recommendation and the remaining consequential decisions that evidence cannot settle. Respect existing accepted decisions. Do not implement, mutate decision records, create throwaway experiments, execute checks, or claim validation from the comparison alone.
