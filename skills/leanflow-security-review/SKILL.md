# Security change review

Read-only, source-only review adapted from Anthropic's security-review procedure and KitShift's evidence guidance. This passive package is not a scanner, CLI/CI action, approval or runtime sandbox. Current task authority wins; planning remains planning and reviewers never execute or fix the target.

1. **Establish the exact basis.** Record the supplied diff and base/head or worktree snapshot, requested paths, requirements and security invariants. If unavailable, state the missing comparison rather than inventing changed lines or substituting a whole-codebase audit. For an explicitly requested planning review of a bounded proposed design, identify the supplied design and current sources instead: report design risks, required controls and unresolved assumptions, not an implemented-change verdict. Missing implementation is not evidence of a defect in nonexistent changed code. Continue unaffected safe inspection and ask only for material facts unavailable from accessible evidence.
2. **Trace relevant behavior.** Read [focused change review](references/change-review.md), then inspect every relevant supplied path and the surrounding callers, enforcement, framework behavior and alternative routes needed to judge its consequence. For the design branch, distinguish proposed guarantees from current implementation and mark implementation-dependent conclusions unverified.
3. **Challenge and disposition.** Read [evidence and challenge](references/evidence-and-challenge.md). Trace each candidate and actively challenge it against the strongest actual controls. Preserve confirmed, needs-validation and rejected decisions, their evidence and decisive gaps. Source-confirmed does not mean runtime-exploited; proposed-design risks are not confirmed implementation vulnerabilities.
4. **Use independence only where warranted.** The coordinator owns scope and integration and may inspect directly or dispatch permitted independent source review through the existing [orchestration delegated-review contract](../leanflow-orchestrate/references/delegation.md#delegated-review). That reference supplies assignment/return rules, not an obligation to start orchestration stages or create roles. No fixed discovery/challenge fleet or model mapping is required. Controller challenge is not independent review; unavailable required independence remains an explicit limit. Review workers do not delegate.
5. **Report bounded results.** State the changed or proposed boundary, basis, inspected/unavailable/deferred/out-of-scope coverage, candidate dispositions and unresolved facts. Label pre-existing concerns separately. Include root-cause-specific remedy recommendations and actual evidence methods. A failed or unusable delegated report is a coverage gap, not proof of safety. No report implies adoption, publication, whole-app assurance or release approval.

All target inspection is read-only: no edits, command/test/payload execution, target/network fetching, credential-location inspection, installs or services. Public-source research is a distinct conditional activity only when separately permitted by the assignment; supplied-source-only restrictions win. Do not silently broaden a small authorization patch into an audit. Do not impose numerical confidence gates or blanket exclusions for AI, availability, dependencies, tests, documentation or client code; relevance follows the actual attacker path and invariant.

Runtime validation requires a separately authorized executor and the safeguards in [runtime-evidence boundary](references/evidence-and-challenge.md#runtime-evidence-boundary). This skill never authorizes a reviewer to perform it or to make automatic fixes.
